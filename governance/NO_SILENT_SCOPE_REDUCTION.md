# Whole-objective closure

The initiating instruction and its full acceptance surface define completion. Decomposition changes the route, not the destination. Only an authorized scope-change record may remove a requirement.

Before execution, record:

- The human outcome and original instruction reference.
- Required behaviors, affected surfaces, persistence and downstream consequences.
- Authority boundaries and explicit exclusions.
- A verification method and evidence destination for each requirement.
- Owners for independent work, with one writer for each mutable subject.

A work item may finish while its parent remains incomplete. Completion messages contain the parent objective status and every open requirement. Use `COMPLETE`, `INCOMPLETE`, or `BLOCKED` precisely. `BLOCKED` names the unavailable input or authority and the work it prevents; independent work continues.

The closure inventory covers direct behavior, shared components, canonical writes, derived views, caches, exports, integrations, permissions, refresh/reopen behavior, failure recovery and affected regressions. For each applicable item, record the exact revision, environment, input basis, observed result and corroborating evidence. Explain an exclusion instead of silently dropping it.

Compilation, a local test pass, a successful deployment or a screenshot alone does not establish the whole outcome. Trace the human action through durable state to its material consumers. Money and other consequential data require independent validation of the input basis.

Before a `COMPLETE` receipt is accepted, the required set must reconcile with the verified set and have no unresolved required remainder. A generated checklist does not prove that its checks ran. `QUALITY_VERIFICATION_LADDER.md` governs independent review where required.

A handoff preserves the original objective, finished effects, unresolved requirements, exact source state and next dependency. It transfers working context and responsibility; it does not close the objective.
